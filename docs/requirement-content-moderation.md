> ⚠️ 이 저장소(`intip-mobile-app`)는 네이티브 WebView 셸이며 포털 UI를 갖지 않습니다(`README.md` 참고). 아래 요구사항의 실제 구현 대상은 **웹 프론트엔드 + 백엔드(포털 서버, 관리자 도구 포함)**이며, 별도 저장소에서 작업이 이루어져야 합니다. 이 문서는 그 작업을 위한 스펙입니다.

## 1. 배경 및 목적

Apple 심사팀은 앱이 "사용자가 익명으로 콘텐츠를 게시할 수 있게 하면서도 적절한 안전장치를 갖추지 않았다"고 판단해 거부했습니다. 원문 요구사항은 다음과 같습니다.

> To resolve this issue, please revise the app to implement all of the following precautions:
> - Age rating must reflect 18+
> - A method for filtering objectionable content
> - A mechanism for users to flag objectionable content
> - A mechanism for users to block abusive users
> - A mechanism for users to immediately remove posts from the feed
> - Developer must act on objectionable content reports within 24 hours by removing the content and ejecting the user who provided the offending content
> - Developer must provide contact information in the app itself, giving users the ability to report inappropriate activity

이 중 **연령 등급(18+)**은 App Store Connect 앱 정보에서 별도로 처리했습니다(완료). 본 문서는 나머지 6개 항목, 즉 실제 제품/운영 기능으로 구현해야 하는 콘텐츠 모더레이션 요구사항을 다룹니다.

## 2. 적용 범위

| 구분 | 대상 여부 | 비고 |
| --- | --- | --- |
| 익명 커뮤니티 게시판 (UGC, 사용자 게시글/댓글) | ✅ 대상 | 성적 노출 등은 커뮤니티 규칙상 금지되어 있으나, 신고·차단·삭제 등 기술적 안전장치가 없는 상태 |
| 인입런 (버스 정보 기능) | ❌ 비대상 | UGC가 아닌 버스 운행 정보 기능. 심사 거부 사유와 무관 |
| 채팅 (`/chat/list`) | 확인 필요 | 1:1/그룹 메시징이라면 신고·차단 대상에 포함 여부를 별도 검토 (Age Rating의 "메시지 및 채팅" 응답과 연동) |

이후 항목의 "게시판"은 익명 커뮤니티 게시판을 지칭합니다. 채팅 기능이 사용자 간 자유 텍스트 교환을 지원한다면 3.2~3.4 요구사항을 채팅에도 동일하게 적용할지 결정이 필요합니다.

## 3. 기능 요구사항

### 3.1 유해 콘텐츠 필터링 (사전 차단)

- 게시글/댓글 등록 시점에 금칙어(욕설, 혐오 표현, 성적 표현, 개인정보 패턴 등) 사전 필터를 적용합니다.
- 필터에 걸린 콘텐츠는 등록을 차단하고, 작성자에게 사유를 안내합니다(전면 비공개 처리보다는 즉시 피드백이 사용자 경험상 바람직).
- 금칙어 사전은 운영자가 관리자 도구에서 추가/삭제할 수 있어야 합니다.
- (선택, 권장) 이미지 첨부가 가능한 경우 이미지에 대한 유해성 검사(자체 룰 또는 외부 API)도 함께 검토합니다.

**수용 기준**: 금칙어 포함 게시글 작성 시 등록이 차단되고, 관리자가 금칙어 목록을 조회/수정할 수 있다.

### 3.2 신고(플래그) 메커니즘

- 모든 게시글/댓글에 "신고" 버튼을 노출합니다.
- 신고 시 사유 선택(예: 욕설/혐오, 성적 콘텐츠, 스팸/광고, 개인정보 노출, 기타)과 상세 설명(선택) 입력을 제공합니다.
- 신고 접수 시 신고자에게 접수 확인 메시지를 노출합니다.
- 신고 데이터는 신고자, 대상 게시물/댓글, 사유, 신고 시각을 포함해 서버에 저장합니다.
- 동일 게시물에 대해 다수 신고가 누적되면(임계치, 예: 3건 이상) 자동으로 노출을 임시 비공개 처리하고 운영자 검토 대기열로 전환하는 것을 권장합니다.

**수용 기준**: 로그인 사용자가 게시글/댓글을 신고할 수 있고, 신고 내역이 관리자 도구에서 목록으로 조회된다.

### 3.3 사용자 차단 메커니즘

- 사용자가 다른 사용자(익명 게시판이라면 익명 식별자 단위)를 차단할 수 있는 기능을 제공합니다.
- 차단 시 해당 사용자의 게시글/댓글이 차단한 사용자의 피드에 노출되지 않습니다.
- 차단 목록 조회 및 차단 해제 기능을 마이페이지 등에서 제공합니다.
- 익명 게시판 특성상 "사용자"의 식별 단위(디바이스, 계정, 세션 등)를 명확히 정의해야 합니다.

**수용 기준**: 사용자가 특정 작성자를 차단하면 이후 해당 작성자의 게시물이 피드/댓글에서 보이지 않는다.

### 3.4 게시물 즉시 삭제(셀프 삭제) 메커니즘

- 작성자 본인이 자신의 게시글/댓글을 언제든 즉시 삭제할 수 있어야 합니다(이미 있다면 유지, 없다면 신규 구현).
- 관리자도 신고 처리 과정에서 게시물을 즉시 비공개/삭제할 수 있는 관리자 도구 기능이 필요합니다.
- 삭제는 소프트 삭제(로그 보존)로 처리하여 이후 악용 사례 추적이 가능하도록 합니다.

**수용 기준**: 작성자 본인이 게시물을 삭제하면 피드에서 즉시 사라진다. 관리자가 특정 게시물을 강제로 비공개 처리할 수 있다.

### 3.5 24시간 이내 신고 처리 프로세스 (SLA)

- 신고 접수 후 **24시간 이내**에 다음 처리를 완료해야 합니다.
  - 신고 대상 콘텐츠 검토
  - 규정 위반으로 판단 시 콘텐츠 삭제 및 작성자 계정 제재(경고/일시정지/영구정지 중 정책 수립 필요)
- 이를 위한 최소 운영 체계:
  - 신고 접수 시 담당자(또는 담당팀)에게 알림(이메일/슬랙 등)이 발송되도록 구현
  - 관리자 도구에 "미처리 신고" 목록과 접수 시각 기준 경과 시간을 표시(SLA 임박/초과 시 시각적 경고)
  - 처리 이력(처리자, 처리 시각, 처리 내용)을 기록
- 운영 인력이 상시 대응 가능한 체계인지(주말/공휴일 포함) 별도로 확인이 필요합니다. 인력이 부족하면 자동 임시조치(3.2의 임계치 자동 비공개)로 초기 대응 공백을 보완합니다.

**수용 기준**: 신고 접수 시각과 처리 완료 시각이 기록되고, 24시간 초과 건을 관리자 도구에서 식별할 수 있다.

### 3.6 앱 내 문의처(연락처) 제공

- 앱 내(웹 포털 내)에서 신고/문의가 가능한 연락 수단을 상시 노출합니다. 예:
  - 마이페이지 또는 설정 화면에 "신고/문의하기" 메뉴
  - 이메일 주소, 또는 인앱 문의 폼
- App Store 심사 가이드라인상 "앱 자체 내에서" 제공되어야 하므로, 외부 링크(예: 카카오톡 오픈채팅)만으로는 불충분할 수 있습니다 — 최소한 이메일 주소 또는 인앱 폼을 기본으로 제공하고, 부가 채널로 외부 링크를 추가하는 형태를 권장합니다.

**수용 기준**: 로그인 없이도(또는 로그인 후) 앱 내 화면에서 문의처를 확인하고 신고를 접수할 수 있다.

## 4. 데이터 모델 (제안)

| 테이블 | 주요 필드 |
| --- | --- |
| `reports` (신고) | id, reporter_id, target_type(post/comment), target_id, reason, detail, status(대기/처리중/완료), created_at, resolved_at, resolved_by |
| `blocks` (차단) | id, blocker_id, blocked_id, created_at |
| `moderation_actions` (제재 이력) | id, target_type, target_id, action(삭제/비공개/경고/정지), actor_id(관리자 또는 시스템), reason, created_at |
| `banned_words` (금칙어) | id, word, category, created_at |

## 5. 운영 프로세스

1. 사용자가 신고 접수 → `reports` 테이블에 저장, 담당자에게 알림
2. 신고 누적 임계치 도달 시 자동 비공개(시스템 처리)
3. 담당자가 24시간 이내 검토 → 위반 확정 시 콘텐츠 삭제 + 작성자 제재, `moderation_actions`에 기록
4. 반복 위반자에 대한 제재 정책(예: 3회 누적 시 영구정지) 수립 및 문서화

## 6. 비기능 요구사항

- **감사 로그**: 모든 모더레이션 조치(삭제, 제재, 신고 처리)는 조치자·시각·사유를 남깁니다.
- **개인정보 보호**: 신고자 정보는 피신고자에게 노출되지 않아야 합니다.
- **성능**: 금칙어 필터링은 게시글 등록 응답 시간에 체감 지연을 주지 않아야 합니다(동기 처리 시 수십 ms 이내 목표).
- **오남용 방지**: 신고 기능 자체의 악용(허위 신고 도배)을 막기 위한 사용자당 신고 빈도 제한을 고려합니다.

## 7. 재제출 전 체크리스트

- [ ] 게시글/댓글에 신고 버튼 노출
- [ ] 사용자 차단 기능 및 차단 목록 관리 화면
- [ ] 작성자 셀프 삭제 + 관리자 강제 비공개/삭제 기능
- [ ] 금칙어 등 사전 필터링 적용
- [ ] 신고 처리 SLA(24시간) 운영 체계 및 처리 이력 기록
- [ ] 앱 내 문의처(이메일 또는 인앱 폼) 노출
- [ ] App Store Connect 연령 등급 재검토 (18+ 반영 여부 최종 결정 — 별도 논의됨)
