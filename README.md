# INTIP — Incheon National University Portal (React Native)

A hybrid (WebView-hosted) app for the INU portal at `https://intip.inuappcenter.kr`.
The native shell provides a **native multi-WebView stack** around the portal plus a
thin JS ↔ Native bridge for login detection, route awareness, FCM push tokens,
cache control, downloads, external-link handoff, and a network gate.
**No portal UI is implemented natively.**

Built with **Expo SDK 56** (dev-client / Continuous Native Generation — `ios/` and
`android/` are generated by `expo prebuild` and are gitignored). The hybrid
contract with the web frontend is specified in
[`docs/requirement-ux-improvement.md`](docs/requirement-ux-improvement.md)
(multi-WebView routing + bridge spec); the original single-WebView parity notes are
kept in [`docs/requirement-scratch.md`](docs/requirement-scratch.md).

## Architecture: SPA + native multi-WebView

The portal is an SPA, but to get native screen transitions, gesture back, and
smooth scrolling, navigation is split across a **stack of native WebView screens**
(spec §1, §3):

- **Main tabs** (`/`, `/home`, `/bus`, `/chat/list`, `/save`, `/mypage`,
  `/timetable`, and their `/m` mobile-prefixed forms) stay inside the **root**
  WebView and switch via in-page SPA routing.
- **Sub-pages** (anything else): the web calls `navigateTo(path, url)`, and the
  shell **pushes a new native WebView screen** (`app/webview.tsx`) so it gets the
  slide-in animation and swipe-back gesture for free. `goBack` pops it.

The web detects the official app from the User-Agent suffix `INTIPApp/1.0.0` plus
the presence of the bridge objects. Because `react-native-webview` exposes a single
`postMessage` channel, the shell **injects shims** that recreate
`window.AndroidBridge.*` (Android) and `window.webkit.messageHandlers.*` (iOS) so
the web's existing environment detection and routing work unchanged (spec §2, §4).

## Bridge protocol

Web → Native messages (names match the original native handlers verbatim):
`navigateTo`, `goBack`, `requestAppUpdate`, `loginSuccess`, `openAppSettings`,
`requestPermissionSettings`, `logWebDiagnostics`, `onLaunchWebCleanupFinished`.
The shell also injects two of its own channels — `routeChange` (history observer)
and `jsAlert` (`window.alert` → native dialog). See `src/webview/bridge.ts`.

Native → Web: `window.onReceiveFcmToken(<token>)` delivers the FCM token (after
each page load, on `loginSuccess`, and on foreground resume — spec §5.A), and
`window.__intipNavigate(<path>)` deep-links the SPA for push taps.

On launch the shell injects a one-time cleanup loop that unregisters service
workers and clears `CacheStorage`, then fades out a branded overlay once the web
signals `onLaunchWebCleanupFinished` (spec §5.B).

## Prerequisites — Firebase config (required)

Push notifications use `@react-native-firebase`, which needs native config files
matching the bundle id `kr.inuappcenter.intip` (set in `app.json`). These are
secrets and are **gitignored** — add them before building:

- `./GoogleService-Info.plist` (iOS)
- `./google-services.json` (Android)

> iOS uses `useFrameworks: "static"` (via `expo-build-properties`), as RNFirebase
> requires. The AppDelegate swizzling proxy is left at its default (we do **not**
> set `FirebaseAppDelegateProxyEnabled = NO`), so APNs tokens are forwarded to
> Firebase automatically.

## Develop

This app uses native modules, so **Expo Go is not supported** — you need a
development build.

```bash
npm install

# Generate native projects (run after changing app.json / native deps)
npx expo prebuild

# Build & run a dev client
npx expo run:ios       # or: npx expo run:android
```

Once a dev client is installed, `npx expo start` serves the JS bundle to it.

Platforms: **iOS 15+ and Android**. (Web is not a target — the portal shell relies
on `react-native-webview` and native Firebase.)

## Release: OTA first, native builds on demand

`.github/workflows/ci.yml` ships changes in two lanes.

**OTA (EAS Update)** — automatic. Every merge to `main` runs `verify`, then
publishes an update to the `production` channel. JS and asset changes reach
users without a store submission.

**Native release** — manual. Run the workflow from the Actions tab and pick a
`platform` (`android` / `ios` / `both`); the default is `none`, so a dispatch
publishes an OTA only. Needed whenever native code changes, or whenever
`expo.version` is bumped.

### Why a version bump forces a native build

`app.json` sets `runtimeVersion.policy: "appVersion"`, so an update only reaches
installed binaries whose `expo.version` matches the one it was published from.
Bump `3.0.6` → `3.0.7` and the next OTA reaches **nobody** until a native
release of `3.0.7` is out. This is the intended safety property, not a bug: it
is what stops a JS bundle from landing on a binary that lacks the native code
it expects.

The `ota-publish` job guards this automatically — if `app.json`, `plugins/`, or
`package.json` changed in the push, it **skips** the publish and says so in the
job summary and the Discord notification. Re-dispatch with `force_ota` if you
know the change was JS-only.

### One-time setup

| Secret | Purpose |
| ------ | ------- |
| `EXPO_TOKEN` | Robot/personal access token from [expo.dev access tokens](https://expo.dev/settings/access-tokens), for an account with access to `gang_03/intip-mobile-app`. |

The `production` channel already exists and maps to the `production` branch.
The job re-creates it only if it's missing, which matters because `eas update`
creates *branches*, never *channels*, while the app requests a channel by name
(`updates.requestHeaders["expo-channel-name"]`) — an update published with no
matching channel succeeds and silently reaches no one. To inspect the mapping:

```bash
eas channel:view production
```

## Runtime permissions

- **Notifications** — requested on first launch. On **Android 13+** the
  `POST_NOTIFICATIONS` runtime permission is requested explicitly (via
  `react-native-permissions` `requestNotifications`); on iOS the APNs prompt is
  requested through Firebase messaging.
- **Camera + Location** — `react-native-permissions` is configured for both
  (`Camera`, `LocationWhenInUse`) and primed once on the first `loginSuccess`,
  so the portal's `getUserMedia` (photo upload) and `geolocation` (campus map)
  work without a second WebView-level prompt. iOS WKWebView geolocation in
  particular needs this app-level authorization. The `iosPermissions` list in
  `app.json` controls which permission handler pods are compiled.

> Adjust the priming trigger in `src/components/WebViewContainer.tsx`
> (`primeWebPermissions`) if you'd rather request camera/location lazily at a
> different point.

## Push notification deep links

Tapping a notification can deep-link into a portal route. Include one of these
keys in the FCM message `data` payload:

| Key     | Example      |
| ------- | ------------ |
| `path`  | `/timetable` |
| `route` | `/bus`       |
| `link`  | full portal URL |

The shell calls `window.__intipNavigate(path)` to navigate the SPA without a full
reload (best-effort: relies on the web app responding to `popstate`).
